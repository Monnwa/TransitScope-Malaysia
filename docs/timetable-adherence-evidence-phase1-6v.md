## Phase 1.6U recovery architecture

| Stage | Durable evidence and enforcement |
| --- | --- |
| Manifest | The reservation transaction creates a versioned manifest keyed by the replay run UUID, with a separate unique request UUID. It pins fixture and baseline checksums, execution mode, candidate IDs and checksums, expected count and the historical replay clock. A partial unique index permits only one uncleaned run in the schema. |
| Candidate registration | The execution journal records actual generation and staging, then commits registration before dispatching an intent. A monotonically increasing journal revision prevents an older update from replacing a newer report. Registration and intent insertion are separate transactions. |
| Intent | The outbox stores the evidence payload and candidate ID. A committed pending intent is independently discoverable. The expected manifest entry and a staged journal entry alone cannot prove persistence. |
| Delivery and receipt | The original delivery function inserts or verifies the archive row and updates its terminal outbox receipt in one PostgreSQL transaction. Successful receipts clear the outbox payload. Recovery claims due intents, calls that function and attempts finalization within one transaction. |
| Discovery and scope | Authenticated `GET ?recoverable=1` finds the one unfinalized run eligible for recovery. `GET ?requestId=<uuid>` recovers the original run ID after an ambiguous reservation response. Authenticated `PATCH ?replayRunId=<uuid>` locks the exact ledger row. It claims only due intents matching the manifest ID and checksum and a durable generation and staging registration. It skips a candidate when its archive checksum conflicts. |
| Finalization | A matching archive and success receipt, a matching failure receipt with no archive, or a durable explicit rejection with no conflicting rows are terminal outcomes. Every expected candidate must be terminal. Zero expected candidates still require an execution checkpoint. Finalization stores the terminal summary and timestamp. Repeating recovery on a finalized run returns the same result. |
| Cleanup | DELETE requires a finalized run and an unchanged terminal summary, and rejects pending, mismatching or unrelated rows. Cleanup retains the manifest, journal and receipt summary as a readable `CLEANED` record, separate from later runs that reuse fixture candidate IDs. |

A fresh request uses the persisted manifest, journal, outbox and archive. It can recover a committed intent without the original process, fixture loader, in-memory GPS history or deferred promises. The original invocation still holds pre-commit payloads, unjournaled observations and an unrecorded parity result. Recovery leaves those gaps visible. An interrupted run may have a finalized archive with its execution state still `INTERRUPTED` and its parity result unset. Candidate checksum comparisons establish correspondence with the pinned manifest and durable records within the trusted database boundary. ### Database permissions

The current `outbox_preview_writer` has SELECT and INSERT on the legacy public archive, SELECT, INSERT and UPDATE on the legacy public outbox, and EXECUTE on its invoker-rights delivery function. It has no DELETE or TRUNCATE on either table. The distinct `outbox_preview_observer` can SELECT both tables and lacks their mutation privileges and delivery function execution. Neither role owns those tables or has CREATE on an application schema. Both roles reported no superuser, database creation, role creation, replication or row-security bypass attributes. Those grants are verified for the old baseline and cannot support the replay worker.

When provisioning is authorized, use a dedicated writer confined to `transit_preview_replay`. Install the archive and outbox migrations with object creation directed to that schema, then apply the replay migration as the schema owner. Verify the exact object definitions, manifest fields and indexes, constrained receipt states, pinned search paths and function execution grants.

| Principal or operation | Required privileges in the isolated replay schema |
| --- | --- |
| Shared replay route role | Schema USAGE and SELECT on the three replay tables. Ledger INSERT on `id`, `request_id`, `manifest` and `report`. Ledger UPDATE on journal and lifecycle columns only, including the cleanup timestamp. Deny UPDATE on manifest, IDs and creation timestamp. |
| Admission and recovery | Outbox INSERT and UPDATE for intents and receipts, archive INSERT, and EXECUTE on the replay copies of `lock_replay`, `finish_replay`, `replay_terminal_summary`, `recover_replay` and the delivery function. These functions run as the caller. |

## Vercel execution and time limits

The route is a dynamic Next.js 15 Node.js handler declaring `maxDuration=60` seconds. The original Deferred Admission path can retain work with `after()`, subject to that invocation's limit. The recovery PATCH instead awaits a PostgreSQL transaction and then reads the per-candidate report in a second transaction. A 200 shows that recovery completed that bounded attempt and the report was read. It can still contain pending or unresolved candidates. A 409 signals a missing or ineligible run. A 503 may reflect a failed request or a commit whose acknowledgement or subsequent read did not arrive. Read the run again and retry the same UUID if eligible. [Route handler](../app/api/internal/preview/evidence-replay/route.ts) · [Next.js `after()`](https://nextjs.org/docs/15/app/api-reference/functions/after) · [Vercel function duration](https://vercel.com/docs/functions/configuring-functions/duration)

Each Neon HTTP transaction has a 1.5-second client deadline. The recovery operation also supplies a 5-second signal, so the shorter 1.5-second limit governs its transaction. The following report query has its own 1.5-second limit. The original replay budget is 35 seconds. The Neon client uses non-interactive HTTP transactions and keeps no application PostgreSQL session across invocations. The PostgreSQL run lock serializes the worker, and its claim is capped at 64 rows. The allowlisted manifest currently contains at most four candidates. Hosted cold start, network and lock wait behavior under these limits remain unmeasured. [Neon HTTP driver](https://neon.com/docs/serverless/serverless-driver) · [Neon pooling](https://neon.com/docs/connect/connection-pooling)

Both Neon roles reported `max_connections=450`, four superuser-reserved slots, zero other reserved slots and no per-role connection cap. Their sessions reported `statement_timeout=0`, `lock_timeout=0` and `idle_in_transaction_session_timeout=5min`. The first two mean no PostgreSQL statement or lock deadline was set for the inspected sessions. The HTTP abort is client-side, and it cannot establish rollback. Confirm the effective replay role settings and measure hosted cold and warm recovery with two calls before relying on the 1.5-second budget. Use provider and PostgreSQL evidence to distinguish client abort, database cancellation and Vercel invocation timeout. The isolated PGlite suite covers manifest and checksum matching, discovery after a lost acknowledgement, refusal of an unknown run UUID, unrelated-row protection, overlapping requests, finalization idempotency, rollback during receipt and finalization, and cleanup refusal. Its overlapping HTTP requests use a single embedded PostgreSQL connection. Separate-session lock contention and cross-instance behavior remain hosted checks. A new regression stops the original adapter after the first of four candidate intents commits. Two fresh requests reconcile the one committed candidate to one archive and terminal receipt. Three candidates remain unresolved, parity remains unset, and cleanup and another reservation in the same schema return 409. [Replay tests](../tests/preview-evidence-replay.test.ts)

For a pre-commit gap, inspect the durable journal and receipts and retain the incomplete run. A new replay of the immutable fixture is a separate experiment. Give it a new request UUID and run UUID and use separately isolated replay storage because the existing uncleaned run holds the schema's only reservation. It cannot supply missing evidence for the old run. A rejected candidate can be terminal only with a durable explicit rejection and no conflicting durable evidence.
