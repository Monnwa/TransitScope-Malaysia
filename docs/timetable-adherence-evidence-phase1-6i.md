# Phase 1.6I — Final evidence archive architecture decision

## Executive summary

**Keep Production archival disabled.** The existing PostgreSQL outbox is the selected architecture for **best-effort archival**, subject to an explicit loss budget and hosted operational validation. It preserves the exact evidence of a committed intent and supports safe same-ID retry. It **cannot guarantee survival of every candidate the application accepts into memory**. Tests through managed HTTPS verified both loss before dispatch and exact recovery after commit.

An application accepts a candidate when it inserts the validated snapshot into its process-local staging map. A committed PostgreSQL outbox transaction is the first durable boundary. The historical archive record and its terminal delivery receipt are a later transaction. This decision preserves those distinctions. Production activation remains blocked by unverified Vercel eviction and invocation-timeout recovery, unmeasured hosted admission reliability, and the need to approve an operational loss contract.

This is a documentation and regression validation phase. The existing classifier, ±120-second threshold, GPS requirements, journey outputs, passenger semantics, application code and database migrations were preserved. The phase made no deployment or Production configuration changes.

## Current durability contract

Here, **accepted** means accepted by the current archive application into its local retry buffer. It is an internal event. A live journey can be served with archival disabled, rejected, pending or committed.

| State | Exact entry condition in the current code | Contract |
| --- | --- | --- |
| **A. Generated candidate** | The server has a directly evaluated current journey result. `captureClassificationEvidence()` re-evaluates the evidence, validates the exact accepted crossing, timetable reference, age, identity and tolerance, then returns a versioned snapshot with stable `recordId` and checksum. A null result does not produce an admissible snapshot. | The candidate exists in process memory and can be rejected or deduplicated before acceptance. Successful passenger classification by itself supplies no archival guarantee. |
| **B. Accepted candidate** | In `ClassificationEvidenceArchive.capture()`, the valid snapshot passes the process-local staged and known-durable ID checks, the serialized batch size check, and both staging limits. **Acceptance is the successful insertion into `this.staged`**, followed by byte accounting and the increment of `counts.captured`. The limits are 2,000 staged records, 4,000,000 serialized bytes, and 256,000 bytes per batch. | It is pending in this process. An invalid, oversized or capacity-rejected snapshot was never accepted. A locally recognized duplicate skips insertion. Scheduling `after`, starting admission, returning HTTP 200 and emitting a pending log leave the snapshot volatile. |
| **C. Durably committed candidate** | PostgreSQL commits the outbox insert for the stable ID. The commit can happen before the application sees it. The application confirms an acknowledged insert, an acknowledged existing ID under the canonical conflict-insert contract, or a positive outbox receipt lookup. Only then does it remove its staged copy and record the ID as known durable. | The committed intent is recoverable independently of the original process, subject to retention, datastore availability and a worker running. This guarantees a durable handoff. Historical archival completes separately when the archive row and terminal `PERSISTED` or `RECOVERED` receipt commit together. |

Code for the three boundaries and receipt settlement. [Candidate capture](../lib/classification-evidence.ts) · [Staging and admission](../lib/classification-evidence-store.ts) · [Feed integration](../lib/processed-bus-journeys.ts) · [Outbox SQL](../database/classification-outbox.sql)

Acceptance counts are per-process events. A different instance or a process whose bounded local cache forgot the ID can accept a repeated candidate for the same ID. PostgreSQL preserves the first committed payload for that stable evidence ID. The identity excludes generation time and later confirmation of the same crossing, while the stored checksum covers the whole original snapshot. Use distinct IDs for cross-instance coverage and compare the original payload or checksum when proving exact preservation.

The **pre-dispatch loss window** starts at B and ends when the first insert is dispatched. Throttling, shared in-flight admission, instance death and the request lifecycle can all leave an accepted candidate in this window. A second vulnerable interval runs from dispatch until actual commit. After dispatch, process or transport failure can leave the application unsure which side of the commit boundary it reached. The current code reports `NOT_COMMITTED` for a pre-dispatch abort or rejection, or for an explicit PostgreSQL cancellation with SQLSTATE `57014`. That status applies to the current attempt. An earlier attempt for the same ID may have committed. Other failed acknowledgements can yield `COMMIT_OUTCOME_UNKNOWN`. A positive receipt establishes durable handoff. A missing receipt at one instant can race a late commit, so retry uses the original ID.

Outbox `PENDING` is a durable intent awaiting a worker. In-memory pending is volatile. `RETRYING` is a committed lease and retry state. `FAILED` is a durable failure receipt, with retained payload, and provides no historical completion. `PERSISTED` and `RECOVERED` attest to archive presence and a terminal receipt under the current migration. A reconciliation success for admission is distinct from the SQL `RECOVERED` delivery state. Post-commit protection lasts within the agreed database durability and retention policy. It does not establish permanent storage or a completion deadline.

## Final architecture comparison

| Option | Pre-commit crash behaviour and recovery | Duplicate prevention and data completeness | Vercel suitability, infrastructure and cost | Can every accepted candidate survive a pre-commit crash? |
| --- | --- | --- | --- | --- |
| **A. Existing PostgreSQL outbox with best-effort admission** | Accepted candidates exist only in the originating process until PostgreSQL commits. A fresh worker can recover committed intents. | The stable ID and PostgreSQL keys preserve one original record and receipt per ID. Completeness is limited by staging pressure, outage, expiry and pre-commit process loss. | Already implemented with the lowest incremental infrastructure. Uses the current PostgreSQL path and bounded application memory. Still needs hosted deadline validation, a reliable worker invocation policy, monitoring and retention operations. | **No.** The current acceptance boundary has verified counterexamples. |
| **B. Durable upstream handoff before accepting a candidate** | Acceptance would occur only after a verified upstream durable acknowledgement for the exact snapshot and its ID. Added infrastructure and operating cost depend on the selected durable store or available input journal. | **C. Verified replay from retained original GPS observations** | A fresh worker could regenerate the exact accepted snapshot if the full reproducible input and its acceptance can be recovered after the crash. | Replay requires the original measured fixes, exact GTFS timetable, run and stop identity, route projection, confirmation, evaluation clock, and applicable algorithm and retention versions. ## Decision 1 — Best-effort archival

**Yes, conditionally.** Use option A as the architecture for best-effort archival if the project explicitly accepts measured pre-commit loss, rejections and delivery delay. The local and managed evidence supports durability and idempotency after PostgreSQL commit. It supports continued validation in an isolated environment.

Documenting operational risk is necessary. Production readiness also requires meeting the hosted evidence gates below. The phase does not approve enabling Production. The Production archive remains disabled while hosted lifecycle and deadline recovery are unverified.

## Decision 2 — Strict durability

**No.** The existing architecture cannot guarantee that every accepted candidate survives termination before PostgreSQL commit. Phase H killed a process after acceptance and before HTTPS dispatch. The accepted snapshot and retry state were lost and no outbox row existed. Awaiting admission and retaining admission through `waitUntil` leave that physical gap in place. Moving the definition of acceptance to PostgreSQL commit would offer a different product contract and would leave the currently accepted in-memory candidates outside it.

If strict durability is mandatory, require an independently durable upstream acceptance receipt or prove exact replay of every accepted candidate. Neither guarantee is implemented or verified by the current architecture.

## Production activation prerequisites

Production activation can be considered only after the following evidence is recorded for the exact reviewed release. This phase neither authorizes nor performs that activation.

1. **Approved loss and latency contract.** Choose best-effort or strict durability explicitly. Before the test, agree numerical bounds for acceptable lost and rejected candidates, maximum pending age, response latency and time to drain a restored backlog. Use distinct IDs and separate generated, accepted, confirmed, archived, rejected, expired and unknown counts. Report an independently counted fixture denominator. Strict durability requires zero loss of accepted candidates across the defined failures and a proven durable acceptance or replay boundary.
2. **Verified Preview and deployment isolation.** A separately authorized controlled Preview must use the reviewed source revision, intended region and isolated credentials. Record actual Node.js version, runtime memory, concurrency or Fluid settings, effective invocation timeouts, cancellation policy and both route configurations. Verify that Production credentials stay absent and the Production gate is effective, including review of missing environment-marker handling. The local guard only rejects the explicit `production` marker and also requires a database URL. [Vercel system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables)
3. **Hosted lifecycle fault results.** In Preview, demonstrate post-response completion and distinguish client disconnect from actual invocation timeout. Exercise a verified host termination or recycle with staged candidates and with committed pending or leased intents. Use independent request and database observations to identify each pre-commit loss, unknown write and post-commit recovery. Exercise at least two distinct hosted instances submitting the same IDs. Verify one archive record and one terminal receipt per expected ID.
4. **Managed transport and recovery under the actual runtime.** Measure cold and warm HTTPS admission and receipt latency from the target region under representative and burst traffic. Capture deadline misses, post-response completion, response parity and backlog age with healthy, slow and unavailable database paths. Demonstrate receipt reconciliation after loss of acknowledgement and managed restart or failover recovery with pending and leased work in isolation. The earlier observed postmaster change only covered settled records.
5. **Reconciled operations and recovery procedures.** Demonstrate how work runs during idle traffic, how it catches up after an outage, and how aged pending, rejected, unknown, failed and recovered candidates are alerted and investigated. Validate least-privilege roles, retention and cleanup, backup/restore readback, disable procedure and integrity checks. Join verified terminal receipts to archive rows and reconcile against the independent fixture IDs. Confirm zero duplicate terminal outcomes, zero altered snapshots and no journey or passenger regression.
6. **Explicit release approval.** Review the Preview evidence against the chosen contract and the remaining risks before a separate activation decision. The current local and managed tests are evidence for the architecture and do not approve hosted use.

## Remaining limitations

- Production fleet coverage, actual managed HTTPS tail latency from the hosted runtime, effective Vercel instance limits and real hosted recovery remain unverified. Fixture counts and timings cannot establish a Production loss budget or service level.
- Pre-commit staging and its counters are process-local. Internal rejection and expiry warnings help explain observed loss, but cannot enumerate every lost accepted ID after a hard crash. A database receipt supplies durable accounting only after handoff.
- Archive payloads reproduce the original accepted projected crossing proof. The current archive schema is not a full journal of original raw GPS observations or a verified deterministic input replay system.
- Request-triggered delivery has no independent liveness guarantee. The default logical retention is seven days after the end of the GTFS service day. Physical cleanup, provider failover and managed backup restoration were outside this phase.
- Implementation and operating costs for B and C are qualitative. The audit selected no service and introduced no infrastructure.
