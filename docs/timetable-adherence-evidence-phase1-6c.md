# Phase 1.6C — Managed PostgreSQL integration and performance validation

## Scope and architecture

Validation used an isolated, temporary Neon Claimable PostgreSQL project in `aws-us-east-2`. The client was the local Windows test runner. It sent synthetic records generated by the existing GPS adherence test fixture through the application’s PostgreSQL archive and outbox adapter. Vehicle IDs carried a `phase16c-` prefix. The inputs represented test-generated classifications and contained no observed transit vehicle history. The PostgreSQL credentials stayed in a private local file outside the repository. The project expires on 12 November 2026 at 23:59 MYT. [Neon Claimable documentation](https://neon.com/claimable-neon)

No application code, database migrations, Vercel settings or production environment were changed. The managed test exercised the production archival gate and verified that configuration returns no archive in a production environment, even with a valid test connection supplied. This phase did not change the ±120-second threshold, GPS evidence rules, GTFS or railway logic, or the passenger-facing classifications.

| Layer | Path exercised |
| --- | --- |
| Capture | The existing evidence builder validates and freezes the crossing pair and original timestamps. The in-memory staging buffer is capped at 2,000 records or 4,000,000 bytes per application instance. |
| Handoff | A validated batch enters the managed outbox using the existing idempotent insert. The durable boundary is the database commit. A client timeout can leave commit status unconfirmed until reconciliation. |
| Claim and delivery | Workers claim up to 64 eligible rows with `SKIP LOCKED`. Delivery inserts the immutable archive row and acknowledges the outbox in one transaction. Unique record IDs and the current claim token protect concurrent delivery. |
| Runtime and recovery | The existing adapter uses Neon’s stateless HTTPS query interface with a pooled endpoint, a 1.5-second query deadline and a 2.5-second drain deadline. In the application, an enabled request invokes the worker after the response. There is no independent scheduler. |
| Database observation | A separate, TLS-verified direct PostgreSQL connection sampled relation sizes and `pg_stat_activity`. A native client pool exercised the pooled TCP endpoint for the connection-exhaustion test. |

The archive-only migration was applied first, an original synthetic record was committed, the outbox migration was applied, and both migrations were reapplied. PostgreSQL 17.11 preserved the original JSON evidence exactly and the application read it back as `VALID_HISTORICAL`. The SQL and lifecycle definitions are the same as in [Phase 1.6A](timetable-adherence-evidence-phase1-6a.md) and [Phase 1.6B](timetable-adherence-evidence-phase1-6b.md).

## Workload methodology

Each timed run started with empty archive and outbox tables on the dedicated test database. The runner generated distinct, valid synthetic records, warmed the HTTPS query path with four read probes, and enqueued records in groups of 64 with delivery paused. After measuring the full backlog, it started the configured number of workers, drained the queue, checked exact table and distinct ID counts, then read 64 evenly spaced records and compared their complete snapshots with the inputs. The same application store and SQL ran in every workload. The 8-second controls use a harness-only deadline and remove the 2.5-second per-invocation drain limit to measure the database-backed queue as a continuous worker. Even the 1.5-second workload rows use a continuous worker loop. The configured runtime was exercised separately during failure and restart tests.

Latency includes the application store call, HTTPS transport, provider routing and database response. The latency tables report nearest-rank P50 / P95 / P99 in milliseconds, followed by the operation count. Each enqueue, claim and archive commit can cover up to 64 records. Read latency is per record. Throughput is successful distinct records divided by elapsed wall time for each phase. These are client-observed timings from a cross-region test. The run did not collect server execution percentiles or isolate network transit time.

### Current 1.5-second deadline

The first unwarmed 64-record enqueue exceeded the deadline at approximately 1.51 seconds. The warmed single-worker 1,024-record run completed at the same deadline. All three higher-concurrency runs hit enqueue timeouts, so the runner captured committed counts and stopped before draining those trial queues. Each longer-deadline control used an empty queue.

| 1,024 | 4 | 4 | 4 | 0 | 256 |
| 5,000 | 4 | 79 | 3 | 4,808 | 4,872 |

Two warm-up reads also timed out in the concurrent 1,024-record run. The independent SQL counts show that an HTTPS deadline is an **unknown outcome** for a write. The database committed some writes whose acknowledgements the client missed. The counts also show that some expected intents were absent at observation time. This is why the worker must retain unconfirmed candidates and retry with their original record IDs. The 8-second controls were diagnostics. They do not establish that increasing the application timeout would be safe within the current 2.5-second request-triggered drain.

## Managed connection and failure tests

Managed PostgreSQL reported a compute-side `max_connections` of 450 with four superuser-reserved slots and no additional reserved slots. The test peaked at 13 sampled client backends and six sampled active backends. The pooled TCP test held two simultaneous transactions and exercised a two-client application pool. The application itself uses stateless HTTPS. The project owner credentials were used for migration and fault injection. A least-privilege deployment role, the provider’s frontend saturation point and cross-region failover were outside this test. [Neon connection pooling](https://neon.com/docs/connect/connection-pooling) · [Neon serverless driver](https://neon.com/docs/serverless/serverless-driver)

The server defaults were `statement_timeout = 0` and `transaction_timeout = 0`. The rollback tests set session-local limits for test transactions. They did not change the database defaults. The transport-blocked cases use an injected client-side outage against the real managed store. The database remained reachable to an independent observer, which could verify commit state.

| Scenario | Observation |
| --- | --- |

| F. Extended unavailability | A 60.00 s application-side outage produced four blocked handoff attempts. An already-committed, leased intent recovered on attempt 2 with its original evidence. The other 1,088 had crossed the durable handoff boundary and still lacked an archive row. |

### Managed compute idle and reconnect

The test committed one identifiable pending intent, closed its database sessions and waited 335 seconds without querying the managed project. The first subsequent HTTPS status call returned `UNAVAILABLE` at 1.50 s. A new TLS-verified direct connection and follow-up HTTPS calls found the intent still `PENDING`, with all 10,904 previously archived rows present. The next worker archived the test intent and read back the exact payload.

**Managed compute restart remains unverified.** The two observations of `pg_postmaster_start_time()` were identical at 9 November 2026, 23:59:21 MYT. The run demonstrated reconnect and durability across the idle window. The anonymous Claimable provisioning flow supplied scoped database access and kept the project management API key on the provider side. A forced compute restart or provider failover was outside this test. [Neon Claimable access model](https://neon.com/blog/an-agent-provisions-a-neon-backend-a-human-claims-it-later)

After the idle check, one continuous control worker drained the remaining 1,025 intents in 11.46 s using the 8-second query deadline. The final SQL audit found 11,993 distinct archive rows and matching outbox receipts, with zero pending or failed. It compared all **1,984** admitted scenario F snapshots against their original fixtures and verified each receipt was `PERSISTED` or `RECOVERED`.

## Volatile staging and evidence reconstruction

Scenario J deliberately withheld the first outbox call. At termination, the oldest of 64 staged candidates had been in memory for approximately 2.03 s and the staged payload totaled 125,700 bytes. All 64 were lost with the process. Replaying the complete original synthetic fixture reproduced 64 record IDs. Replaying the same cases with no original fixes produced zero eligible records. The test could replay those snapshots because the fixture retained the original fixes, scheduled inputs, run identity and classification time. A production worker restart has no guarantee that those inputs remain available, and reconstructing a classification would require the original qualifying observations and evidence. Creating a new result from present tracking state cannot recover the original historical snapshot.

In scenario F, 2,400 candidates arrived at the start of the simulated outage. The byte limit admitted **1,984** and rejected **416** before handoff. Staging held 3,999,036 bytes and still held the same candidates at the 60-second check. All admitted candidates eventually had durable intents, including 381 whose handoff was acknowledged as already queued. The recovery loop used an 8-second harness query timeout and retained the application's 2.5-second per-flush deadline. The worker reported seven enqueue failures in total, including the four injected failures, plus seven recovery failures. It had confirmed 704 archive writes, while PostgreSQL already contained 896 archive rows for the staged candidates. This difference again shows that a client-side failure can leave a committed result.

At the staging limit, the local process reported 111.26 MiB RSS and 45.37 MiB used heap, up from 92.17 MiB and 35.75 MiB immediately before the burst. This includes fixture generation and harness allocations.

For this burst, candidates remained staged across the full 60-second outage. The staging buffer was empty by 107.01 s from the start of the burst. Those are observed bounds for the longest residence in scenario F. The harness sampled application counters at flush boundaries, so an exact per-candidate maximum for that burst is unavailable. Scenario J directly measured residence through process termination.

If the product requires recovery of every eligible classification through a database outage or a worker termination, durable upstream staging or replayable inputs are necessary. The present design can support a narrower guarantee that begins at outbox commit, subject to retention, retry limits and a running worker. Document which guarantee is required before choosing another datastore or queue. This phase preserves the current staging architecture.

Storage figures are PostgreSQL relation sizes including indexes. At 10,000 records, 19.35 MiB of serialized evidence used 18.19 MiB of outbox relations before drain. Immediately after drain, the archive and outbox occupied 55.70 MiB together. Successful delivery clears the payload from live outbox rows. MVCC dead space and indexes can still occupy relation bytes until maintenance, so the immediate post-drain size is useful for backlog provisioning and cannot be treated as the long-term size of receipts alone. The benchmark did not measure billed storage, WAL, vacuum reclamation, database compute memory, or the production classification arrival rate.

Memory is for the local Node benchmark process, sampled around operations. It includes the TypeScript fixture loader, pre-generated inputs and result handling. It cannot establish the memory footprint of the live Next.js process or explain the earlier Preview OOM. PostgreSQL activity counts were sampled roughly every 750 ms and include the monitoring session and provider client backends. Short-lived peaks may fall between samples.

Seven-day evidence retention is the current default. Historical reads enforce the evidence cutoff and the outbox can settle expired or exhausted work as `FAILED`. Physical removal of expired archive rows, terminal outbox receipts and failed payloads requires an operational cleanup policy. Plan capacity against the actual classification rate, age distribution, active backlog, update churn and cleanup behaviour. The temporary provider quota is 100 MB of storage and 1 GB of transfer. Production cost and long-run storage remain unmeasured. [Neon Claimable limits](https://neon.com/claimable-neon)

## Regression and production readiness

**Keep production archival disabled.** The managed database validated the schema, original evidence readback, deduplication and recovery after an outbox commit. The concurrent runs also showed that the current application deadline can expire during a successful commit, and the controls that drained all records used continuous workers and, at higher concurrency, a longer query deadline. Production backlog service levels and trigger cadence still need validation. The precommit termination test demonstrated data loss.

Before any activation decision, validate the real per-invocation drain in an isolated environment colocated with the selected database, under steady arrivals and cold starts. Measure acknowledgement ambiguity, retry reconciliation, age of the oldest pending intent and failure counts. Establish a way to wake workers after inactivity, alert on expired or exhausted intents, and clean up retained evidence and receipts. Size and test a least-privilege runtime role and retention policy on the chosen provider. Preserve the original evidence validation and the ±120-second classification rule in that work.

The Neon driver wrapped observed HTTPS aborts in `NeonDbError` with a nested `TimeoutError`. A query deadline that fires before the shared drain deadline can therefore be logged by the current outer-error check as `DATABASE_ERROR`. Separate query and drain timeouts in any future operational measurements.
