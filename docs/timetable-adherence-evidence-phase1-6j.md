# Phase 1.6J — Architecture freeze and hosted validation plan

## Architecture freeze

Freeze the Phase 1.6I decision for **best-effort archival**. The accepted design uses bounded in-memory staging, opt-in Deferred Admission, a PostgreSQL outbox, and retries with the original evidence ID. Capacity rejection, pending admission, and an unknown commit outcome remain explicit. PostgreSQL protects an intent after commit. A later worker can deliver that intent with the original evidence after the originating process exits. **Production archival remains disabled.** This phase records the design and plans a future Preview run. [Phase 1.6I decision](timetable-adherence-evidence-phase1-6i.md)

| Boundary | Frozen contract |
| --- | --- |
| Generation | `captureClassificationEvidence()` constructs a validated, versioned snapshot from the original crossing evidence and schedule. Its stable `recordId` identifies that evidence version. A run-stop can have distinct IDs for distinct evidence versions. |
| Acceptance | `ClassificationEvidenceArchive.capture()` accepts a candidate when `this.staged.set()` inserts it into the originating process's in-memory buffer. Current limits are 2,000 records, 4,000,000 serialized bytes, and 256,000 bytes per batch. Invalid proof, an oversized snapshot, and lack of capacity can reject an attempt before acceptance. |
| Admission | With `TRANSIT_CLASSIFICATION_DEFER_ADMISSION=1` and a request retainer, the route registers admission with Next.js `after`. Without deferred retention the route awaits admission. Either path uses volatile staging. Returning a journey, scheduling continuation, or dispatching a write supplies no durable receipt. |
| Durable commit | The outbox transaction commits for the stable ID. Acknowledged insertion, acknowledgement of an existing ID under the schema, or positive receipt reconciliation lets the application confirm that boundary. An interrupted acknowledgement can leave a committed intent unconfirmed. Retrying the same ID preserves the first committed payload. |
| Historical delivery | An eligible worker claims a committed intent and uses a fenced lease. The archive row and terminal `PERSISTED` or `RECOVERED` receipt commit together. A durable `FAILED` receipt is a delivery failure. Delivery depends on database availability, retention, and another worker running. The routes trigger work on requests and have no independent wake-up mechanism. |

**Acceptance does not mean durable persistence.** A process crash after staging and before dispatch can permanently lose the candidate. A dispatched candidate is still vulnerable until PostgreSQL commits. After dispatch, a failed acknowledgement and a single negative read leave room for a late commit. The current architecture provides no strict pre-commit durability guarantee. Phase 1.6H demonstrated pre-dispatch loss and post-commit recovery in controlled managed HTTPS tests. Both hosted eviction and hosted invocation-timeout recovery remain unverified. ## Controlled Vercel Preview validation plan

### Entry conditions and instrumentation

1. Use an authorized, access-protected Preview of the reviewed revision with the existing archive migrations in an isolated managed PostgreSQL database or branch. Scope the least-privilege archive credentials and deferred flag to that Preview. Verify the effective `VERCEL_ENV` and credential scope without exporting values. The current guard returns early for `VERCEL_ENV=production` and also requires `TRANSIT_CLASSIFICATION_DATABASE_URL`. Independently verify Production has no archive URL and the existing guard applies. Leave Production settings and data untouched. [Configuration guard](../lib/classification-evidence-store.ts) · [Vercel system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables)
2. Record the deployment revision, Node.js runtime, region, memory, Fluid Compute and concurrency settings, effective invocation duration and cancellation policy. The current Node routes declare `maxDuration=60`. The dashboard aborts its request at 55 seconds. The archive uses a 1.5-second HTTPS query timeout and a 2.5-second admission operation budget. These are distinct clocks. Next.js `after` permits work after the response within the route's execution budget. A successful HTTP response supplies no evidence that the continuation finished. [Transit route](../app/api/transit/route.ts) · [Bus journey route](../app/api/bus-journey/route.ts) · [Next.js `after`](https://nextjs.org/docs/15/app/api-reference/functions/after) · [Vercel function duration](https://vercel.com/docs/functions/configuring-functions/duration)
3. Replay deterministic synthetic observations through the journey pipeline with exact GTFS fixture data. Predeclare expected eligible IDs and original payload checksums. Run matched archive-disabled and deferred Preview controls for both routes, with the same inputs and clock. Verify journey and classification parity, including the existing ±120-second threshold, GPS requirements and passenger-facing status. A trial that generates zero eligible candidates is a no-op and cannot pass an admission scenario. [Managed HTTPS fixture precedent](timetable-adherence-evidence-phase1-6h.md)
4. Keep an external run manifest and event log that survives function termination. Record scenario, stable ID, checksum, boundary timestamps, request and invocation IDs, a per-process marker, and the last observed attempt outcome. For precise crash tests, require a test-only barrier after verified staging insertion and have the external controller acknowledge receipt of the ID before injecting the fault. Use a separate PostgreSQL observer for outbox and archive readback, including the original checksum, lease state and terminal receipt. A planned fixture ID alone proves neither generation nor acceptance. A crash before the independent acceptance witness is a measurement gap. Disclose it and withhold the affected cohort's loss-rate conclusion unless the denominator can be reconciled. This is validation instrumentation and is outside the application acceptance path. [Vercel runtime logs](https://vercel.com/docs/logs/runtime)
5. Separate deliberate fault cohorts from representative load runs. Include cold and warm requests, representative fleet cadence, a burst near the staging limits, and an idle period followed by an eligible worker request. Agree recovery and latency bounds before running. For each cohort report response-ready, admission, acknowledgement and delivery timing, with sample counts and applicable percentiles. Record backlog, oldest pending age, staged bytes, rejection reasons, timeout origin and retries. Label client-observed timing as such. Report PostgreSQL execution or commit timing separately only when directly observed.

### Scenario matrix

For every row, parity with the archive-disabled control is required whenever a journey response completes. Report **Pass**, **Fail**, or **Unverified**. A pass requires the planned fault, independently observed boundaries and reconciliation. A known pre-commit loss can pass a fault-characterization test while still counting against the proposed loss budget for that fault cohort. Apply the common cleanup below after each row.

**Common cleanup.** Stop fixture traffic and remove the fault. Take a final read-only snapshot of run-scoped IDs and archive receipts before any deletion. Wait for old invocations, transactions and leases to settle, or quarantine the disposable test database until they have. Keep the sanitized manifest and timings for review. Remove only the isolated fixture data or disposable database under the approved cleanup procedure, then revoke the test-only credentials when the validation ends.

**Capability limits.** Access to a precise hosted termination control, per-instance lifecycle events, and correlation of post-response timeout with archive work has yet to be established. If Preview cannot expose these boundaries, obtain a provider-supported fault and trace facility or a disposable lifecycle-controlled runner for the process-level tests. A runner can establish application failure behaviour. Only a directly observed hosted event can close the corresponding Vercel gate. An observed managed database path fault also leaves provider restart or failover behaviour unverified unless a managed restart or failover with pending work is separately observed. ## Proposed data-loss budgets

These are **policy scenarios**. No rate has been selected and no hosted or Production loss rate has been measured. The daily cohort is the set of distinct IDs first accepted in a Malaysia Time calendar day. The limit is the floor of `unique accepted IDs × policy rate`. If traffic estimates count generated candidates, measure acceptance separately before using the table.

| Proposed maximum | 1,000 accepted/day | 5,000 accepted/day | 10,000 accepted/day | 50,000 accepted/day |
| ---: | ---: | ---: | ---: | ---: |
| 0.1% | 1 | 5 | 10 | 50 |
| 0.5% | 5 | 25 | 50 | 250 |
| 1% | 10 | 50 | 100 | 500 |
| 2% | 20 | 100 | 200 | 1,000 |

### Candidate lifecycle accounting

| Measure | Counting rule |
| --- | --- |
| Generated | Count distinct valid snapshot IDs emitted by candidate generation. Keep invalid-evidence attempts without a snapshot ID as separate diagnostics. |
| Accepted | Count the first proven insertion into staging per stable ID across all instances and requests. Report subsequent staging events separately. Assign a reattempt or late commit to the original cohort. |
| Committed | Count distinct accepted IDs with a proven PostgreSQL outbox commit, including commits independently observed after a lost acknowledgement. Separately count verified terminal archive delivery and durable delivery failures. |
| Rejected | Record attempts by reason. Report distinct valid generated IDs that were explicitly rejected and never accepted by the cutoff. A later acceptance moves that ID into the accepted cohort while preserving the earlier attempt metric. Track unresolved admission outcomes separately from confirmed rejection. |
| Pending | Separate volatile staging, unknown commit outcome, and durable outbox awaiting delivery. A pending outbox row already counts as committed. |
| Permanently lost | Count only proven accepted IDs that remain absent from PostgreSQL once relevant attempts have settled and whose original staged evidence is gone with no demonstrated recovery path. An apparent loss from one instance can still reconcile via the same ID from another. |
| Unreconciled | Count proven accepted IDs for which the agreed cutoff leaves no proven commit or confirmed loss. Break out live pending, unknown acknowledgement and missing tracking evidence. An unproven acceptance is a denominator gap to report separately. |

Set the cutoff before the run and allow the planned restore, retry and lease windows. Reconcile the accepted cohort as `committed + confirmed lost + unreconciled` at that cutoff. Report `confirmed lost / accepted` as the observed lower bound. For a policy gate use the conservative bound `(confirmed lost + unreconciled) / accepted`. Keep the bounds separate from rejection and failed delivery rates so an apparent improvement cannot come from accepting fewer candidates or leaving more committed intents undelivered. A cohort with zero accepted IDs has no loss-rate denominator. Report deliberately induced faults separately from representative traffic. Neither can establish a Production rate without comparable Production evidence.

## Dashboard observability assessment

The passenger dashboard and its Technical information section show transit feed and announcement health. The transit API's `busEvidence` describes GPS history persistence, which is separate from PostgreSQL classification archival. The archive's process-local `status()` and logs can explain individual attempts. They cannot reconcile all generated and accepted IDs across processes. [Dashboard](../components/dashboard.tsx) · [Transit API](../app/api/transit/route.ts) · [Archive status](../lib/classification-evidence-store.ts)

| State | Existing internal evidence | Remaining gap |
| --- | --- | --- |
| Generated | Snapshot exists in the capture path. | No independent count or inventory of all generated IDs. |
| Accepted | `captured` increments on staging insertion. The deferred pending log reports a buffer snapshot. | Volatile and can count repeat IDs across instances. |
| Committed | `candidateOutcomes.committed` counts confirmation events. SQL supports lookup by ID and separate terminal archive verification. | Confirmation totals can double count repeats or lag actual commits. Reconcile using distinct durable IDs. |
| Rejected | Rejection counts and warnings distinguish invalid proof, capacity and oversized snapshots. | Attempt totals cannot identify final unique rejected IDs or recover diagnostics lost with a process. |
| Pending | `staged`, `stagedBytes`, `oldestPendingMs` and `pendingUnknown` describe local admission. PostgreSQL records durable pending and retrying intents. | Local pending disappears on termination. Durable pending needs independent age and backlog monitoring. |
| Lost or unreconciled | Local expiry and unknown-commit counters explain observed cases. | They cannot enumerate all hard-crash losses. PostgreSQL contains only candidates that reached its commit boundary. |

For Preview, the minimum additional visibility is the external test manifest with observed generation and acceptance events, correlated to current worker logs and read-only SQL. If the existing logs cannot supply a needed boundary, add a structured event only in the separately reviewed validation fixture. Use the stable ID and boundary timestamps without raw GPS or credentials. Any future operational view should separate process counters from distinct database receipts and expose unreconciled IDs or coverage gaps. This phase changes no dashboard or telemetry code.

## Production activation prerequisites

1. Approve a **best-effort** policy with numeric limits for pre-commit loss, rejection, delivery failures, pending age, response latency and backlog recovery. If strict durability is required, the frozen architecture cannot meet that requirement.
2. Verify Preview isolation, the exact release revision and effective runtime settings. Independently verify that Production credentials are absent and the Production guard is effective during validation. The current guard would need a separately reviewed release decision before any future activation.
3. Close the hosted lifecycle gates with correlated evidence of real invocation timeout and actual eviction or recycle. Demonstrate post-response completion, same-ID concurrency across instances, and fresh-worker recovery. Missing host evidence keeps activation blocked.
4. Reconcile a representative Preview workload against the approved limits. Demonstrate original checksums, no duplicate terminal receipts or false persistence claims, bounded outage behaviour, and recovery after restoration. Verify managed restart or failover with pending and leased work, or keep that prerequisite open.
5. Demonstrate the operator's recovery procedure during idle traffic, backlog monitoring and escalation, retention and cleanup, least-privilege access, backup readback and disable procedure. Submit the hosted report for a separate activation decision.

Phase 1.6J produced a plan only. No Preview tests were executed and no application or infrastructure changes were made. The regression suite was not rerun because this phase only added documentation. The last recorded confirmation was 353 unit tests, 100 Chromium tests, TypeScript, ESLint and a local production build.
