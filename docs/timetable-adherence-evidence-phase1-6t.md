# Phase 1.6T — Protected Replay API Security and Architecture Audit

The replay API passed local security and journey parity checks after targeted isolation fixes. **Do not deploy the draft as-is for hosted failure testing.** The route still relies on a verified disposable database binding, and its recovery API cannot yet recover all interrupted runs. No Preview or Production archive flag, credentials, deployment protection, or cloud configuration was changed. The draft and this audit remain uncommitted.

The audit covered the Phase 1.6S working tree on `feature/postgres-outbox-preview`, based on `d1f9c3ffa27008a0df7491e024d5679b780fa1a2`. The Phase 1.6Q captures and canonical baseline were unchanged. This phase used local tests with embedded PostgreSQL. It did not test hosted authentication, a managed database, or Vercel invocation termination.

## Production isolation and authentication

| Boundary | Finding and local evidence |
| --- | --- |
| Deployment environment | The original handler checked only `VERCEL_ENV`. It now requires both runtime `VERCEL_ENV` and `VERCEL_TARGET_ENV` to be exactly `preview`, and rejects when normal archival is explicitly enabled. Missing, unexpected and conflicting metadata fail closed. Tests use a correctly formed, valid Preview token and verify rejection before database construction or continuation registration. HEAD and OPTIONS now also go through the guard. Unsupported methods are rejected by the framework or handler. |
| Authorization | The handler requires a configured URL-safe bearer token of 32–128 characters and compares equal-length valid candidates using Node's `timingSafeEqual`. Missing credentials, malformed configuration and equal-length incorrect credentials were rejected. The length and format checks are public constraints, not entropy guarantees. Use a randomly generated, branch-scoped token and keep deployment protection enabled. The token is a shared operator credential with no individual attribution. |
| Request inputs | Only four operations reach the replay logic. POST requires JSON, one UUID request ID and enumerated fixture, mode and fault values; unknown fields and query parameters are rejected. GET, PATCH and DELETE accept only one UUID run ID. Tests confirm that database connection settings, environment overrides, SQL, paths and executable fields never reach the storage connector. The only file reads are the two pinned server fixtures, with SHA-256 checks and decompression limits. |
| Database binding | The only writer URL read by the replay handler is `TRANSIT_PREVIEW_REPLAY_DATABASE_URL`. A test fails if the normal archive URL is accessed. SQL is fixed and request-derived values are bound as parameters. No replay code calls a Vercel configuration API. A schema boundary and a separately named environment variable do **not** prove physical database identity. A misconfigured operator can still point Preview at the wrong database. Hosted binding and role provenance are required before enabling replay. |
| Normal transit route | The live route imports the normal processor and normal archive only. Replay switches, fixture selection and faults exist only in the separate internal handler; query parameters and the bearer on a normal demo request did not invoke replay. The existing live fleet route regression also passed. |
| Error and secret handling | Responses are `no-store`. A simulated connection exception returned only the fixed 503 body and did not produce a raw console error or warning. The shared archive logs fixed labels and counts, not raw database exceptions. Local client build output was checked with synthetic canaries (results below). Vercel platform and Neon log redaction were not tested. |

## Execution isolation and request limits

Each run builds its own timetable, GPS history, journey processor, journal and optional archive instance. Fixture inputs are frozen and no replay code writes to `process.env` or the normal archive singleton. The disabled mode instantiates no archive and records no staging candidates or outbox writes. It still writes a replay reservation and report to the isolated ledger. The separate replay writes flag controls enabled POST modes and PATCH; authorized cleanup remains available with that flag off. Synchronous mode awaits admission through the journey processor. Deferred mode hands off the in-flight admission promises to the route's retained callback. The full 21-output digest matched the original disabled baseline in both modes. Each enabled mode produced four committed intents, four archived rows and four terminal receipts with the same candidate IDs.

The request parser streams up to 1 KiB with a 1.5-second read deadline. Fixture decompression is bounded; a run has a 35-second cooperative deadline, individual Neon HTTP transactions use a 1.5-second client abort, and the route declares a 60-second maximum. Client abort is not proof that PostgreSQL rolled back. A unique partial index allows one uncleaned run in the shared database, another unique index prevents request-ID reuse, and the replay ledger row serializes guarded operations across transactions. Concurrent POSTs produced one 202 and one 409 locally. This limits fixture-backed writes but is not a per-client request rate limit: authorized GETs and rejected POSTs still consume resources, and cleaned ledger rows accumulate. Keep this an operator-only tool; add route-level limits if access or usage expands, and define a capped ledger retention policy that preserves the intended request-ID deduplication window.

## Candidate reconciliation and cleanup

| State | Evidence required and verified locally |
| --- | --- |
| GENERATED / STAGED | The archive capture callback records actual generation and insertion into the in-memory staging map. A pinned expected candidate is not counted as generated before its callback. Generation time is the historical fixture clock, not the wall-clock dispatch time. |
| ADMISSION_PENDING / UNRESOLVED | A held admission produced a journey response and one pending candidate with zero committed, archived or terminal records. An unconfirmed candidate after the run ends or expires is unresolved. Neither an expected ID nor a journaled attempt proves a PostgreSQL request was sent or committed. |
| COMMITTED | A matching outbox payload checksum, or a successful payload-cleared receipt paired with a matching archive row, is required. Lost acknowledgement was reconciled through persisted rows and did not produce a false failure. |
| ARCHIVED / TERMINAL | Archive identity and stored checksum must match. A successful terminal receipt needs the matching archive and a payload-cleared success state. A terminal failure needs a matching outbox payload and the database failure state. Aggregates come from candidate rows. A checksum match is a comparison to the pinned fixture's identity, not a new hash of the stored payload. |
| Duplicate submission | Repeated and overlapping writes for the same ID produced one outbox and archive identity and one terminal row per candidate. The replay transaction lock serializes database mutation within a run; this is not evidence of global exactly-once delivery. |

The Phase 1.6S worker acquired due rows across the entire replay schema. It now limits **both** ordinary replay delivery and fresh-worker recovery to the staged candidate ID and checksum pairs for that run. The existing live archive claim remains unchanged when no scope is provided. The local fresh-worker test recovered the matching committed intent and preserved an unrelated pending row and its attempt counter.

The original cleanup could return success with unexpected rows left in the replay schema. It could also use the deleted archive ID as a substitute for verifying ownership of a payload-bearing outbox row. Cleanup now locks the run and rejects pending or retrying intents and any unexpected or mismatching rows before deleting anything. A payload-cleared successful receipt is eligible only with matching archive evidence. It preserves unrelated rows in the normal schema. A cleaned old run cannot remove a newer run's records; simultaneous runs are prevented by the reservation index. Cleanup is still destructive by design after reconciliation: export the candidate report and receipts before DELETE. The ledger keeps the request-ID tombstone, but GET does not serve a cleaned run. These guarantees assume the disposable schema has no independent writers bypassing the run lock.

The replay transaction and replay-schema functions now search `pg_catalog` first, the replay schema next, and `pg_temp` last. The replay migration also revokes default public execution for its copy of the delivery function. Apply this migration in the isolated schema and grant only the replay role the required access. The normal archive migration and schema were not changed. ## Deferred Admission and deployment blockers

The route uses Next.js `after()` to await admission tasks and finalize the report within the invocation. Work may start before the response; the continuation keeps the invocation open after response completion subject to the platform's execution limit. This does not create a durable queue. A process termination or invocation timeout can destroy staged evidence before PostgreSQL commit. A committed intent survives the process and a fresh local store recovered the controlled, finished `after-commit` case. That fault skips delivery and simulates an adapter error after a real local commit; it does not stop a Vercel instance. The outage hook is also an adapter simulation. Eviction, timeout, cross-instance contention, managed transaction cancellation and recovery are unverified. [Next.js 15 lifecycle](https://nextjs.org/docs/15/app/api-reference/functions/after) · [Vercel duration](https://vercel.com/docs/functions/configuring-functions/duration)

| Remaining issue | Consequence and recommended remediation |
| --- | --- |
| Interrupted-run recovery | PATCH and its database guard require a finished `after-commit` run. An invocation killed after committing an intent but before finalizing its ledger can leave a durable, pending row that neither PATCH nor DELETE can clear. Add run-scoped recovery for expired unfinished runs based on journaled ownership and actual durable rows. Validate without reclassifying missing evidence as committed. |
| Recovery clock | PATCH always uses fixture end time plus two seconds. If a worker commits a claim but does not deliver, the retry time advances while repeated PATCH calls use the same frozen time. Separate historical evidence time from a bounded advancing worker lease clock, and test interruption between claim commit and delivery. |
| Reservation acknowledgement | A reservation can commit while its HTTP acknowledgement is lost. An idempotent request retry gets 409 without the run ID. Provide an authenticated lookup or idempotent response keyed by request ID. Preserve the original reservation rather than rerunning it. A killed invocation can also lose journal events recorded only in memory; report the resulting uncertainty. |
| Hosted identity and observability | Before a separately authorized deployment, verify the source SHA, branch-scoped flags, disposable Neon identity and role grants, absence of access to normal archive schemas, and redacted log correlation. With protection intact, verify denied non-Preview calls and test normal operation with writes off. Only then consider managed writes under separate authorization. Compare actual durable rows and receipts after hosted interruption; record unsupported scenarios as unverified. |

**Readiness:** Suitable for local deterministic replay. Keep hosted replay writes off until recovery and provenance gaps are addressed. Production archival remains disabled; neither this audit nor a later successful Preview test would establish a guarantee before commit.
